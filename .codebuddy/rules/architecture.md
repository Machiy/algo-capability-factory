# 架构与验证约束

规则分两层：`题目硬要求` 来自 `llm_agent.md`，不可裁剪；`本项目设计选择` 是为评分与可复现性自定的实现约束。若设计选择与实现冲突，改规则并同步 `PLAN.md`，不要硬扛。

## 题目硬要求（不可裁剪）

- 四层验证缺一不可：接口规范、功能正确性、指标表现、运行稳定性（任务 5）。
- 知识图谱的检索结果必须进入 Planner 与 Coder 的 prompt，不能只做静态展示（创新性评分点：图谱增强生成与验证）。
- 生成代码必须在子进程沙箱中执行，并具备超时、内存上限与 AST import 白名单（加分项：代码安全检查与沙箱执行）。具体数值以 `configs/default.yaml` 的 `runtime` 段为准，不在本规则重复定义。
- 模块间只通过 `factory/contracts/` 的契约数据类交互，避免硬编码与不可维护设计（代码质量 30%）。
- 新任务类型通过新增 `verify_*.yaml` 与指标插件接入，不修改核心验证器（进阶要求：插件式接入）。

## 本项目设计选择（可调）

- 六层结构：contracts / knowledge / agents / runtime / validation / 接入层；换分层方案时同步更新 README 第 2 节与 `PLAN.md` 第 3 节。
- 修复必须先分类错误签名再定向处理，最多 3 轮；每轮结果回写知识图谱。
- 测试集仅在终评使用一次；指标门槛以 `configs/verify_*.yaml` 为准，不硬编码。
- 统一 `logging` 与结构化运行轨迹，作为「错误处理和日志记录」评分项的证据；P5 验收含 ruff / pytest 全绿与干净环境一键复现。
