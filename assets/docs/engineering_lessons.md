# 工程教训库（系统层面）

本文件记录本项目在真实运行中踩过、且**换任务依然成立**的系统级坑点与教训。
与 `assets/docs/data_dictionary.md` 的已知数据问题（T1–T4）不同：那四条只对
信用卡数据集成立，本文件的条目属于平台、沙箱、验证语义、图谱与 LLM 通路。

一条合格的教训必须同时给出：**现象**（能观测到什么）、**根因**（系统层面，
不是这一次的输入）、**处置**（改什么）、**预防**（怎么提前避免）。缺根因或
缺处置的条目只是日志，不得进入本库。

## 教训速查

| 编号 | 类别 | 现象 | 根因 | 处置 | 预防 | 适用面 |
|---|---|---|---|---|---|---|
| LE1 | 运行环境 | 内存看门狗永不触发，占用早已超过 2GB 仍判定通过 | Windows 虚拟环境里的 `python.exe` 是重定向器，读父进程 RSS 只有约 4MB，按单进程计量完全失真 | 改为 `psutil.Process.children(recursive=True)` 对整棵进程树求和，超限即终止子进程 | 资源基准与四层验证共用同一套内存口径，并构造超限用例验证看门狗真的会触发 | 跨场景通用 |
| LE2 | 平台 | 本地跑通的 CLI 断言在 CI 上随机失败 | Typer 检测到终端后自动着色，输出里混入 ANSI 转义序列，按纯文本匹配必然失配 | 子进程设 `NO_COLOR=1`、`TERM=dumb`，断言前统一剥离 ANSI | 所有 CLI 断言走同一个输出归一化函数，不各写一份 | 跨场景通用 |
| LE3 | 平台 | 证据 SHA-256 在 Windows 上校验失败，Linux 正常 | Git 检出的换行是 CRLF，与原文 LF 不同，同一内容算出不同哈希 | `read_sources` 读入后归一化换行再计算哈希 | 哈希只对归一化后的文本计算，测试重算时复用同一入口 | 跨场景通用 |
| LE4 | 验证 | 报告写着四层验证，实际只有两层在生效：确定性恒为 True，test 段从未被读取 | 检查项只存在于报告字段里，没有代码真正读取对应输入 | 沙箱支持 `repeat>=2` 的同进程二次 fit 与 `segment="test"`；工作流在候选比较结束后消费一次 test | 每个检查项都必须配一个「不通过」的构造用例，否则不许写进报告 | 跨场景通用 |
| LE5 | 图谱 | 边很多，但追问「这两点为什么相连」答不出来 | 连边按 `index % len(metrics)` 轮转，与内容无关，属于凑数量 | 改为名称或属性文本命中才连边，宁可边少 | 每条边都要能回答「凭什么连」，答不出就删 | 跨场景通用 |
| LE6 | 编排 | 修复退化成反复重试，同一错误连修三轮仍失败 | 没有先分类错误签名，直接整段重新生成代码 | 建立「签名 → 策略」表，只改必要片段，最多 3 轮 | 每轮修复必须记录签名与策略，重复签名立即停止该路线 | 跨场景通用 |
| LE7 | 平台 | 传入 `../../x` 的请求能把产物写到仓库外 | 把用户输入原样拼进文件名，只做了字符串拼接 | 接口层做字符集 pattern 校验并拒绝 `..`，工作流侧再兜底一次 | 任何用户输入进入路径前先校验字符集与相对路径，双层校验 | 跨场景通用 |
| LE8 | LLM | 报告里把离线回放说成实时调用，评审无法区分 | 响应来源没有落到产物里，只在日志里出现 | 把来源写进 `RunTrace.interpreter_source`，报告逐条标注 | 任何「实测」结论必须能追溯来源，回放内容单独标注 | 跨场景通用 |
| LE9 | LLM | Coder 明明调用了 LLM，产物却全是模板代码 | LLM 返回的代码没过静态检查就被丢弃，且丢弃原因没有留痕 | 先过 AST 白名单与契约检查，通过即采用；失败回退模板并写 `code_sources` | 回退路径必须写进 trace，不能静默回退 | 跨场景通用 |
| LE10 | 运行环境 | 同一候选两次 fit 的指标不同，报告却声称确定性通过 | 随机种子未固定，或同一进程重复 fit 带来状态污染 | 显式固定 `random_state`，并在子进程内二次 fit 比较输出 | 确定性必须实测（最大绝对差），不能靠声明 | 跨场景通用 |
| LE11 | 检索 | 图谱做得很全，但生成代码看不出受过它影响 | 渲染与注入是两套逻辑，检索结果只用于展示 | 统一走 `RetrievalResult.as_prompt_context()`，Planner 与 Coder 强制使用 | 注入内容要写进 trace 留证，报告可回放 | 跨场景通用 |
| LE12 | 编排 | 换一个任务类型就要改核心验证器，改动风险高 | 任务假设（指标、划分、数据列）写死在代码里，而非配置里 | 指标与门槛下沉到 `verify_*.yaml`，新增任务只加配置与插件 | 新增任务类型时不许改核心模块，只允许新增配置与注册插件 | 跨场景通用 |

## 使用方式

- 抽取器把本文件「教训速查」的每行折成一个 `Lesson` 节点，`signatures` 用于
  与运行期错误签名自动匹配；
- 检索器把教训按「置信度 → 出现次数」排序后注入 Planner 与 Coder 的 prompt，
  生成代码必须遵守，报告第 1 节可见注入内容；
- 运行期失败案例按签名累积，独立运行达到阈值（默认 2 次）后自动提升为教训，
  与本文件的种子教训共用同一套字段与检索路径；
- 若某条教训被后续实践推翻，应修改本文件并在 `status` 上标注 deprecated，
  而不是直接删除——删除会让后来者重新踩一遍。
